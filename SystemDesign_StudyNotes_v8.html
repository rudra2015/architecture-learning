Foundations

Architecture vs Design

A blueprint for the system — not the brick-by-brick build.

Architecture is the high-level blueprint: it manages complexity, defines the major components and how they coordinate, and selects the right hardware. Design is the lower level — how each component is built internally (class/sequence/state diagrams, pseudocode, DB normalization, OOAD). Different jobs; don't mix them.

The course frames architecture through the Rational Unified Process (RUP) — two halves: modeling (how you represent it) and goals (what it must achieve). The modeling views run Use cases → Component → Logical → Process → Deployment (plus hardware).

Real world

The deployment view then says which .exe runs where (Client.exe, Banking.exe, DB.exe across Server-1/2/3 with sized RAM and disk).

Architecture goals — the four "-ilities"

What every architecture is judged against.

  • Scalability — handle growing work (users/data/transactions) without losing performance.
  • Reliability & High Availability — reliability is the probability of failure-free operation for a given time; HA minimizes the impact of unplanned outages.
  • Flexibility — adapt to changing requirements/tech without hurting quality.
  • Modularity — separate modules, connected but not dependent; expose an interface, hide the implementation.
Real world

Scale for a Black-Friday / IPL-final surge to millions; survive a node failure because peers take over; AWS RDS Multi-AZ flips to a standby when the primary dies.

Distributed systems

Many machines, one system.

A distributed system is many computers across a network — often across geographies — working together as one. We use it to beat the limits of a single machine: it's scalable (many machines), reliable (a peer takes over on failure), and secure (a hybrid setup hosts the app in a public cloud and data in a private one; proxies hide where the real server lives).

Networking & Infrastructure

The OSI model

Where each device and protocol lives.

Anchors: switches are L2 (MAC, frames), routers are L3 (IP, packets), L4 is transport (TCP/UDP, ports). TCP is connection-oriented, reliable, slower; UDP is connectionless, faster, not reliable.

DNS, NAT, switches & routers

The core services and boxes inside a network.

DNS translates a hostname to an IP (a distributed hierarchy of name servers) so you type netflix.com not an address; it can return a list of IPs. NAT maps private IPs to public ones before the internet (router/firewall) because internet routers drop private IPs — Static (1→1 fixed), Dynamic (private→pool), PAT (one public IP, a port per device).

A switch (L2) connects servers by MAC and keeps a switching table (MAC↔port) plus a VLAN table; a VLAN splits one physical network into several virtual ones. A router (L3) connects networks via IP, keeps a routing table built by OSPF, and uses Dijkstra for the shortest path.

Router vs L3 switchA router connects networks (bigger table, lower throughput); an L3 switch connects devices (smaller table, higher throughput).

Data-centre topology

3-tier vs spine-leaf, and the path a request takes in.

3-tier (Core → Aggregation → Access) is optimised for North-South traffic. Spine-leaf wins for the East-West microservice traffic of modern clouds: every leaf connects to every spine, so any server reaches any other in ≤ 1 hop — lower latency, fewer bottlenecks, fewer switches.

VPN & tunneling

A private network stretched across the public internet.

A VPN anonymizes your traffic and location and extends a private network to remote users by building a tunnel between a VPN client and server. Tunneling is encapsulation — wrapping one protocol inside another. L2TP: a Layer-3 protocol (IP) carries a Layer-2 payload (an Ethernet frame — MAC, ARP, non-IP). IPsec secures the tunnel so CIA is met.

Real world

OpenVPN, Cisco AnyConnect, NordVPN. WFH access to the office network, or reaching a geo-locked service via a server in another country.

The traffic cop in front of a server pool.

A load balancer spreads traffic so no server is overworked, reroutes on failure, and auto-adds new servers. Requests go through the LB; responses go directly back to the client.

Consistent hashing

Add or remove a server without re-shuffling everything.

The modulo problem

Naive modulo hashing sends a key to hash(key) mod N. It works until N changes — then almost every key moves:

Modulo example (N: 10 → 11)Naveen 99 → 99 mod 10 = 9, 99 mod 11 = 0
Rudhra 112 → 112 mod 10 = 2, 112 mod 11 = 2
Nikhil 92 → 92 mod 10 = 2, 92 mod 11 = 4
add one server and most keys remap → the whole cache is relearned

The hash ring

Place servers (hashed from their IP) clockwise on a ring; a key is hashed too and goes to the nearest server clockwise. Add/remove a node and only a fraction of keys move.

Real world

Partitioning in Amazon DynamoDB and Apache Cassandra; spreading keys across distributed-cache nodes.

End-to-end: typing www.facebook.com

The flow as taught in the Load Balancer session — DNS, access path, NAT, DNS load balancing, data centre.

This is the worked example from class: how a request leaves your laptop, crosses your ISP, gets a public address, is steered to the right data centre, and is balanced onto a server — framed as a Layer-4 load balancer scenario.

Phase 1 · Name → IP (DNS)

DNS resolves www.facebook.com to 10.34.45.67 — the IP of Facebook's load balancer, not a single server. A DNS server can return a list of IPs (one per data centre).

Phase 2 · Out of your home + NAT

Your laptop has a private IP (10.45.67.84) from the Wi-Fi modem. The request travels Wi-Fi modem → OLT (optical line terminal) → edge router → core router, through the ISP (Airtel). Before the internet, NAT maps the private IP to a public IP (23.45.78.21) from a pool — internet routers drop private IPs.

Phase 3 · Pick the data centre (DNS load balancing)

Facebook runs data centres in SFO, London and Mumbai, connected by optical cables, each with a Cluster Manager and its own load balancer. The DNS server is "intelligent" and returns the nearest healthy data centre; the cluster managers talk to each other, and if a data centre goes down its load-balancer IP is removed from the DNS list.

Phase 4 · Inside the data centre (LB → services)

The request hits the load balancer (10.34.45.67), which spreads it across servers — e.g. an account service and a ledger service. This is a Layer-4 LB (routes on IP + port, no content inspection); a Layer-7 LB would read the content and send Zoom / SQL / cache / tool requests to different servers. Internally: Router (L3) → external firewall → switch (L2) → servers. The conversation is a REST API over HTTP over a TCP socket to a listening port, with a header (destination address, port, length, protocol) and a body.

Phase 5 · Logged in? Sticky session

When you log in (username/password → a token), a sticky-session load balancer pins all your requests to the same server holding your session. Without it, each request can land on a different server and shared state is read from a cache/DB. Responses go directly back to you, not through the LB.

Real world

Airtel/Jio as the ISP, your home router doing NAT, Facebook's data centres behind geography-based DNS load balancing, and a sticky-session LB once you've logged in. Open Uber, ICICI or Instagram and the shape is identical — only the destination DC and services change.

Virtual machines, hypervisors & Docker

Two ways to package an application — heavy isolation vs lightweight sharing.

A virtual machine is a software container that simulates a physical computer — it can run its own OS and apps as if it were real hardware. Virtualization lets one physical server run multiple OSes or sessions simultaneously. A hypervisor (a.k.a. VMM) is the software/firmware that creates and manages VMs on a host.

Real world

AWS EC2 uses a Type-1 hypervisor — it's called a "hosted VM" only because AWS manages the hypervisor for you, not because it's Type-2. Docker — engine, build/run flow, registries

Docker packages an app + dependencies into a portable container that runs on any Linux/Windows host. Docker Engine is client-server: a long-running daemon (dockerd), APIs for programs to talk to the daemon, and a CLI client. Note: a Linux Docker Engine cannot run a Windows container.

Worked example: an Ubuntu image with NGINX baked in. docker pull nginx fetches it from Docker Hub; docker run -d -p 80:80 nginx starts a container, mapping port 80. NGINX itself is a high-performance web server, reverse proxy, load balancer, and API gateway widely used in microservices.

How fast — and how expensively — you want to survive a data centre failure.

All three modes keep a secondary data centre ready to take over if the primary fails. They differ in how powered-on the standby is, how fresh its data is, and how fast it can take over.

Hot standby fits banking/trading systems (Zerodha-NSE style flows) where availability cannot be compromised. Cluster architecture — the pattern behind Google, Hadoop & Kubernetes

One master node tracking many worker nodes — the blueprint nearly everything else copies.

A cluster has one master node and many worker nodes (just servers). The master keeps a metadata database — IP addresses of each worker, what data/files live on which worker, and which worker holds backup copies of which data. On top of that data, it performs three actions: heartbeats the worker nodes, delegates traffic from clients to the right worker, and decides replication — who backs up which data.

Single point of failure? A data centre runs many master nodes, not one — they ping each other, and if one goes down the others take over (and traffic-routing systems like web crawlers stop sending it work). One master going down should never bring the cluster down.
Real world

This single pattern — tweaked — underlies Google File System (search engine), Hadoop/HDFS, Apache Spark, and Kubernetes. Kafka itself is a copy of the Broker pattern + Leader Election. As Naveen put it: the architects who invent these reusable patterns (Larry Page/Sergey Brin with GFS, Neha Narkhede with Kafka) become extraordinarily wealthy from the architecture alone, not the code.

Google File System (GFS)

How Google turns a 10 GB website crawl into split-second parallel processing.

GFS is Google's proprietary distributed file system (not to be confused with the Linux GFS) — built for the search engine's core storage needs. It is the cluster-architecture pattern, specialised: instead of a generic "master/worker," GFS uses a Master Server and Chunk Servers.

GFS termCluster equivalentRole
Master ServerMaster nodeHolds metadata: which chunks live on which chunk server; distributes files; heartbeats chunk servers; sets file-access lease time
Chunk ServerWorker nodeStores the actual file chunks on disk (not in a database — real files)

Every file the master splits a crawled page into is capped at 64 MB per chunk, and each chunk gets a 64-bit globally unique name. GFS keeps at least 3 replica copies of every chunk, spread across different chunk servers/data centres.

Why chunking helps: Google crawls ~6 billion websites. Splitting each site's data into small chunks and spreading them across thousands of chunk servers lets the whole crawl be processed in parallel in split seconds — instead of one server working through it serially.
Real world

Hadoop's HDFS, Apache Spark, and (per Naveen) even YouTube's video chunking on upload follow this same GFS pattern. Today, the 6 billion crawled pages also feed Transformer-architecture models (encoder/decoder, self-attention, feed-forward networks) — the same data pipeline that powers GFS-era search now trains LLMs like ChatGPT and Gemini, which is part of why traditional search is losing relevance to AI chat interfaces.

The open-source cousin of GFS — same pattern, different names, plus a parallel-processing algorithm.

Apache Hadoop is an open-source, Java-based framework that copies the GFS/cluster-architecture pattern using low-cost commodity hardware instead of expensive supercomputers/mainframes. HDFS (Hadoop File System) is its distributed file system: fault-tolerant, high-throughput, built for huge data sets, and able to scale by adding or removing nodes as load changes.

MapReduce is the algorithm Hadoop uses to process huge files in parallel across many nodes, then combine the results.

The smallest deployable unit — and how Pods find and talk to each other.

A Pod is the smallest, most basic unit of deployment in Kubernetes — a logical host for one or more containers that share storage (volumes) and network (one shared IP + port space per Pod). A Deployment creates Pods with containers inside them, not containers directly; Kubernetes manages Pods, not containers.

Pod stateMeaning

Pods are ephemeral — once one dies, an identical Pod is rescheduled elsewhere; the old one is never resurrected. Single-container Pods (one container wrapped by a Pod) are the common case; multi-container Pods are reserved for tightly-coupled containers that must share resources directly.

Controllers — the supervisors

Controllers compare the desired state (what the admin wants) against the current state of the cluster and act to reconcile the two — creating Pods, replacing failed ones, scaling the count up or down.

  • Jobs — one-time tasks: a backup run, a batch data job.
  • Deployments — always-available apps: websites, online stores. Replication controller keeps the replica count correct.
  • StatefulSets — apps that must remember things: databases, file servers. Database data lives in Persistent Volumes (PVs), not inside the Pod — PVs are part of the cluster storage layer and outlive any single Pod, giving the persistence, consistency and durability a database needs.

Pod-to-Pod communication

  • Containers in the same Pod talk via localhost + port.
  • A container can reach another Pod by IP directly — the CNI plugin (Calico, Flannel, Cilium) handles the routing between nodes.
  • More commonly, a container reaches another Pod through a Service, which has a stable IP and a DNS name (e.g. my-service) resolved by Kubernetes' own DNS server, CoreDNS — this survives individual Pod IPs changing.
Real world

Account Service (a Pod) needs to call Inventory Service (another Pod) — interpod communication via a Service + CoreDNS means Account Service never has to track Inventory Service's raw, changing IP. A Backend Pod talking to a Cache Pod (Redis) is the same pattern: each component runs in its own Pod for isolation/scaling but cooperates as one logical application.

Kubernetes security, namespaces & resource governance

Locking a Pod into its own boundaries, and stopping one Pod from starving the cluster.

Pod security context

A Pod's securityContext hardens the container: runAsNonRoot: true and runAsUser: 1000 stop it running as root; allowPrivilegeEscalation: false blocks privilege escalation; readOnlyRootFilesystem: true locks the container's own filesystem; capabilities: drop: [ALL] strips unneeded Linux capabilities. Pods should also avoid host networking (sharing the Node's IP/ports, bypassing the CNI layer), hostPath mounts (reading/writing the host's filesystem), and sharing the host's PID/IPC namespace — each of these lets a compromised Pod reach beyond its own boundary into the Node itself.

Network Policies

By default Kubernetes allows all Pod-to-Pod traffic. A NetworkPolicy with an empty podSelector: {} and both Ingress/Egress in policyTypes denies everything in a namespace by default — you then selectively allow only the traffic you need. Enforcing this needs a CNI that supports it: Calico, Cilium, or Weave Net.

Apache Spark — in-memory, DAG-driven processing

The same master/worker shape as Hadoop, but data stays in memory and a DAG plans the work first.

Apache Spark is an open-source distributed computing engine for big-data processing — known for speed and in-memory computation, with libraries for SQL, ML (MLlib), streaming, and graph processing, and support for Scala, Python (PySpark), Java and R. It follows the familiar master/worker pattern.

Spark componentRole
Driver ProgramEntry point of the Spark app — converts user logic into tasks and distributes them; talks to the Cluster Manager and Executors. The Driver never talks to the client directly — the client talks to the Cluster Manager (master)
Cluster ManagerAllocates resources across the cluster — standalone, Hadoop YARN, or Apache Mesos — and dynamically adjusts allocation to demand
Worker NodePhysical machine running one or more Executors
ExecutorRuns on a worker node, holds a subset of data partitions in memory, executes tasks, caches intermediate results, reports status back to the Driver

RDD, DAG & lineage — Spark's fault tolerance

A Resilient Distributed Dataset (RDD) is an immutable, fault-tolerant, distributed collection held in memory for fast access. Every transformation (map(), filter()) creates a new RDD and is lazy — nothing executes until an action (collect(), count(), saveAsTextFile()) is called. Spark tracks how each RDD was derived from the previous one — its lineage — forming a DAG (Directed Acyclic Graph: directed edges, no cycles).

Lineage examplerdd1 (textFile) → rdd2 (filter "ERROR") → rdd3 (map) → rdd4 (reduceByKey)
worker holding rdd3's partition crashes → Spark replays only that step from the lineage graph — no full replication needed, unlike HDFS blocks

When an action triggers execution, the DAG Scheduler breaks the graph into stages (a new stage begins wherever a shuffle/data-transfer-between-nodes is required) and then into tasks, each handed to an Executor. Once all stages/tasks finish, results return to the Driver.

Real world

Naveen's framing: Spark deliberately skips Hadoop's "replicate every block 3x" safety net — since the lineage graph alone is enough to recompute a lost partition, Spark trades replication storage cost for in-memory speed. This is why Spark is the go-to for iterative ML workloads where the same data is scanned repeatedly.

Forward hides the client; reverse hides the servers.

A proxy is an intermediary between client and real servers, adding firewall/filtering, connection sharing and caching. Data Structures

LRU cache

Evict the least-recently-used item in O(1).

An LRU cache orders items from most- to least-recently-used so the stalest item is always known. A doubly linked list (queue) holds the items, and a hash map maps each key to that node's address. On access, move the node to the head; when capacity is hit, evict from the tail. The map stores the node's address, so you find and move any node in O(1) without scanning. Cost: O(n) space across two structures.

Real world

Redis allkeys-lru eviction, the OS page cache, your browser cache, CPU caches.

Graphs — the vocabulary

Non-linear: vertices joined by edges.

A graph is a set of vertices (nodes) and edges connecting them — like a cyclic tree, but with no parent-child relationship.

  • Adjacent — two nodes joined by an edge. Path — sequence of nodes from one vertex to another. Cycle — no repeated edges/vertices, first = last.
  • Weighted — each edge carries a positive weight w(e): distance, cost or time.
  • Undirected / Connected / Complete — both ways / a path between every pair / every pair joined (n(n-1)/2 edges).
  • Back edge — in DFS, an edge to a visited ancestor; signals a cycle.
Real world

Social networks (LinkedIn connections) and the road network behind Google Maps are graphs; edge weights become distance, fare or latency.

BFS & DFS

Queue goes wide; stack goes deep.

BFS is level-order using a queue (FIFO): add a node, print and dequeue it, then enqueue its unvisited neighbours — never repeating. DFS goes as deep as possible using a stack (LIFO): push one neighbour at a time to the deepest node, then backtrack, checking for any vertex you missed.

Real world

BFS: shortest hops, friend suggestions, web crawlers, broadcasting. DFS: cycle detection, topological sort, finding articulation points.

Tarjan & Dijkstra

Critical junctions, and the shortest path.

Tarjan's algorithm finds Strongly Connected Components (in a directed graph, groups where every node reaches every other) and articulation points / bridges — critical junctions whose removal breaks the graph.

Dijkstra's algorithm finds the shortest path from a source to all vertices in a weighted graph. Set the source to 0 and every other node to infinity, then repeatedly relax edges, always keeping the lowest value at each node.

Tarjan: critical routers/switches, network reliability, dependency cycles. Dijkstra: Google Maps, ClearTrip/Expedia route & fare search, OSPF link-state routing.

Microservices

Microservices architecture — from component to service

Day one of a chapter Naveen warned is "very large" — not finished in two or three classes. This is the starting shape.

Component-based architecture (the banking example from Part 01) has one shared database behind several components. Microservices changes that: it is an architectural style that structures an application as a collection of independently deployable services — never call them "components" once you're in microservice-land, that word is wrong here.

Database-per-service pattern

Each microservice owns its own database (DB1, DB2, ...) and full data ownership/independence. A microservice can never reach another microservice's database directly — it must go through that microservice. This is a named design pattern: Database per Service.

API Gateway + registry

A client request lands on the API Gateway, which looks up a registry to find which service should handle it, then routes the call there (e.g. to the Bank Transaction service). Service boundaries are typically carved out using Domain-Driven Design.

Sync vs async inter-service communication

  • Synchronous (REST APIs) — one service calls another directly and blocks waiting for a reply. Used when you need an immediate answer.
  • Asynchronous (Kafka / message broker) — used when the caller doesn't need to wait; the underlying foundation of microservices communication is the RPC (Remote Procedure Call) model either way.

Pods running different instances of the same or different microservices still need to find and reach each other — this reuses everything from the Kubernetes section: interpod communication via localhost (same Pod), Pod IP (cross-Pod, via the CNI), or a Service + CoreDNS (the most common, IP-change-proof option).

Real world

Account Service wanting to talk to Inventory Service is Naveen's running example: client → API Gateway → Account Service (its own Pod, own DB) → Inventory Service (its own Pod, own DB) via interpod communication. Swiggy, Zomato, Uber and Facebook are "nothing but a bunch of microservices on the cloud" behind an API Gateway.

Why it matters: microservices let an architect break one large, complex application into independently deployable pieces — faster feature delivery, independent scaling per service, and no single point of failure for the whole app. The trade-off is the complexity of inter-service communication and data consistency across separate databases — which is why this is "a very large chapter."

What the API Gateway actually does

One box on the diagram, a dozen jobs behind it. Naveen's full list — the ones marked as design patterns get their own treatment below.

Every client request — mobile, web, whatever — terminates first at the API Gateway, which sits as one of many servers behind a data centre's routers, firewall and switches (that topology detail is "implicitly understood" and usually dropped from diagrams). From there, the Gateway is responsible for:

  • Request validation — checks HTTP method, header and body against predefined rules. Underlying transport is sockets; REST sits above HTTP, which follows CRUD (POST=Create, GET=Read, PUT=Update, DELETE=Delete). An oversized body is a classic attack: a hacker sends a huge, invalid payload purely to make the Gateway burn time validating it (e.g. 30ms work stretched to 10s) — covered properly under security later.
  • Whitelisting / blacklisting — allow-list and deny-list rules at the Gateway level for strict access control.
  • Authentication & authorization — verifies credentials (API key, username/password) and enforces access policy, often via an external identity provider (Azure AD) or cloud-native IAM (AWS IAM: users, groups, policies). Covered in detail below.
  • Service discovery — looks up the service registry to find which backend microservice should handle the request, since microservices register their REST APIs with the registry on startup.
  • Protocol translation, dynamic routing, error handling, circuit breaking, observability/monitoring, caching (often via a distributed cache like Redis), SSL termination — Naveen flagged these as coming later, once security and circuit-breaking get their own chapters.
  • Rate limiting — gets an entire dedicated chapter (Part 07) because of how much an architect needs to reason about it.
Interview framing: the items marked in yellow on Naveen's slide are named design patterns — interviewers love asking "what is the Proxy/Edge Service pattern?" by name even when they're not checking whether you can actually design anything.

Auth service, JWT, and the Proxy/Edge Service pattern

Banking example throughout, since — as Naveen put it — everyone can relate to a bank balance.

Login flow

  1. Client sends a login request (username + password) to the API Gateway.
  2. Gateway forwards it to the Auth Service.
  3. Auth Service checks the credentials against its store and returns a JWT (JSON Web Token).
  4. The JWT is handed back to the client through the Gateway.

Every request after login

The client must attach the JWT to every subsequent request (e.g. "get my bank balance"). The Gateway validates the token — often via a distributed cache holding active tokens, so it doesn't have to round-trip to the Auth Service each time — and only on a valid token does it forward the request to the target microservice.

Password hashing

Passwords are never stored in plaintext or in a reversible "encrypted" form — they're passed through a hashing algorithm and stored as a hash. Hashing is one-way: given the hash, you can never recover the original password. On login, the entered password is hashed again and compared against the stored hash; a match authenticates, a mismatch doesn't. This is also why nobody — not even bank customer-care staff — can ever "look up" your password.

Multiple devices, multiple tokens

The same user logging in from mobile and from web gets two different JWTs — one per device/session, not one per user. The Gateway keeps track of which token came from which request by tracking IP address (and often device type, the way Facebook can tell iPhone vs Android) — that mapping is how it knows "this JWT is the mobile session" vs "this JWT is the web session" even though username and password were identical.

Real world

Rudra logs in from his mobile and from his laptop with the same banking credentials. Mobile gets JWT-1, laptop gets JWT-2. When "Rudra-web" later asks for a bank statement, the Gateway already knows — from IP/device tracking at login — which token belongs to which device, and validates accordingly.

Multi-factor authentication

The Auth Service can call out to a third-party OTP provider's REST API as part of authentication — client gets an OTP on their phone, submits it back through the Gateway to the Auth Service, which confirms with the OTP provider before issuing the JWT. Google Authenticator-style flows work the same way.

Role-based access control

Users belong to groups, and groups carry a set of permissions. A "normal user" group can see only their own account balance; an "admin" group can see anyone's. AWS IAM models this directly: IAM Users, Policies, and Groups, with policies attached to roles.

Proxy / Edge Service pattern

Whenever you bolt authentication, routing, or request filtering onto the API Gateway before a request reaches an internal service — using access tokens/JWTs to secure the call — that's the Proxy or Edge Service pattern. "Edge" loosely means "close to the customer side," though in practice it's just shorthand for anything (auth, load balancing, routing logic) integrated directly into the Gateway layer rather than pushed into the microservice itself.

Design principle: supporting functionality — auth, caching, load balancing — belongs in the API Gateway, not the microservice. The microservice's job is the actual business logic; loading it up with cross-cutting concerns defeats the point of separating services.

Aggregator pattern & Chained (orchestration) pattern

Two more "yellow" interview terms — both about how the Gateway talks to multiple microservices for one client request.

Aggregator pattern

Used when a single client request needs data combined from several microservices — a dashboard or user-profile screen being the classic case. The Gateway calls every relevant microservice in parallel, aggregates the responses, and returns one combined payload.

Real world

A monthly financial dashboard pulls bank balance, credit card balance, mutual fund balance, bond balance and equity balance from five separate microservices — all fetched in parallel and aggregated into one dashboard response instead of five separate screens.

Used when microservices must be invoked sequentially rather than in parallel — the output of one call feeds into the next, so they can't be fired off all at once. Not the right fit for the dashboard use case above, but necessary whenever a workflow has a genuine order dependency between services.

Circuit breaking — closed, open, half-open

What happens when the microservice a client is calling is itself talking to a service that's failing.

Take Service A calling Service B, and Service B's own database has a non-transient failure (it's not coming back after a quick retry). Left alone, Service A keeps sending requests that Service B can never fulfil, burning threads and connections on both sides — and the failure risks cascading upstream to whatever calls Service A. The Circuit Breaker pattern exists to stop that.

  • Closed — normal state, all requests reach the service; the breaker just counts recent failures. If failures exceed a threshold within a time window, it flips to Open.
  • Open — requests are rejected instantly without ever reaching the failing service, protecting it from being overwhelmed further. After a fixed timeout, the breaker moves to Half-Open.
  • Half-Open — a restricted number of trial requests are let through. If they succeed, the breaker closes and normal traffic resumes; if they fail, it reopens and the cycle repeats.

The API Gateway is usually the natural place to host this: it already sees every call to every downstream service, so it can detect high latency/timeouts/errors centrally and, once tripped, either route to a fallback (cached data, a default response) or return a clear error — instead of letting every caller independently keep hammering a service that's already down.

Related patterns: Retry pattern — automatic reattempts with back-off for transient errors. Bulkhead pattern — isolate failures by partitioning resources (separate thread/connection pools per downstream dependency, so one slow dependency can't starve the others). Timeout pattern — stop waiting on a slow response rather than let it block indefinitely.

Domain-Driven Design — clear boundaries & aggregates

How an architect actually decides where one microservice ends and the next begins.

Break along business sub-domains

Microservices are carved out using Domain-Driven Design (DDD) — split by real business capability, not by technical layer. Orders → Order Service, Payments → Payment Service, Catalog → Product Service, Customers → User Service, Delivery → Shipping Service. Done this way, each service maps to a function the business actually understands, a team can own and understand its own domain end to end, and coupling stays loose while cohesion inside each service stays high.

Single Responsibility Principle

Each microservice should do only one thing well. Order Service should not send emails — a separate Email Notification Service owns all emails. Mixing responsibilities into one service is exactly the anti-pattern DDD boundaries are meant to prevent.

Bounded context, entities, aggregates

  • Clear boundaries (bounded context) — a service is built around a business capability, not a technical component. Order Service owns order entry, order rules, order database — never split it into a "parsing component" or "protocol component."
  • Entities — objects with identity that live inside exactly one microservice: Order, Customer, Product, each keyed by its own id.
  • Aggregate — a cluster of entities and value objects that change together, with one root. Order (root) groups Order Item, Delivery Address and Payment Status; every change to the cluster must go through the root — order.addItem(), order.markAsPaid(), order.cancel() — so the aggregate can never end up in an inconsistent state.
  • Value objects — immutable, no identity of their own, just a value: an address, an email.
  • Event-driven communication — when something significant happens inside one domain, it emits an event (e.g. Connection_Added_Event) rather than another service reaching in directly.
Golden rule: a microservice never reads another microservice's database — not even for a quick lookup. All cross-service access goes through that service's own API or its published events.

When two services are coupled — Payment ↔ Account

The DDD rule "never read another service's database" is easy to state and hard to live with once two domains genuinely depend on each other.

Payment Service needs to debit a balance that only Account Service owns. Since Payment can never touch Account's tables directly, it has three legitimate options:

  1. Synchronous REST call — Payment sends POST /accounts/{id}/debit with the amount and a transaction id; Account checks balance/limits/status and replies {status:"success", newBalance:14500} or {status:"insufficient_funds"}. Payment marks its own record success/failure based on that response — the two stay loosely coupled even though the call is synchronous.
  2. Event-driven (async) — the same interaction modelled as an event instead of a blocking call, so Payment doesn't wait on Account.
  3. CQRS (Command Query Responsibility Segregation) — Payment keeps a read-only, eventually-consistent copy of the balance for fast reads (high-traffic dashboards); Account Service alone still owns the write model and every update.

When the two fall out of sync

Sequence: Payment asks Account to debit ₹500 → Account succeeds, ledger updated → Payment tries to mark its own record "success" but that write fails (DB down, network blip). Now Account has already deducted the money while Payment's own status is stuck — a real consistency problem, not a hypothetical one.

Fix: if the status update fails, the message stays in a queue (Kafka, RabbitMQ) and a consumer keeps retrying until it succeeds; alternatively Payment can self-heal later with GET /accounts/transactions?paymentId=123 to reconcile itself against Account's record.

If they're permanently out of sync

Real payment systems — UPI/NPCI, Paytm, Razorpay, Stripe, PhonePe, Amazon, Uber — all follow one principle: the Account/Ledger is the golden source and Payment Service is derived state. If Payment's own copy can never be fixed, it doesn't actually matter — payment status can always be reconstructed from the ledger. What none of them do is roll back the transaction on the Account side just to keep Payment's local copy tidy.

Two-Phase Commit vs the Saga pattern

Two different answers to "how does a transaction that spans several microservices actually commit?"

Two-Phase Commit (2PC)

A controlling node coordinates a set of participating nodes (microservices) through two phases:

2PC — two phasesPhase 1 (Prepare) — controller asks every participant "ready to commit?"; each replies yes/no.
Phase 2 (Commit) — if everyone said yes, controller tells all to commit; if even one said no, controller tells all to roll back.

The cost: the whole system is only as fast as its slowest participant, since a ready node must sit and wait for confirmation from every other node before anything commits — the coordinator's constant back-and-forth ("chattiness") drags overall performance down. In this model the API Gateway typically does not participate in the commit protocol itself; its job stays limited to receiving the client request and routing it to the right service.

Saga pattern

A Saga does not use two-phase commit at all. Instead it's a sequence of independent local transactions, each in its own service, coordinated either by choreography (event-driven, no central controller) or orchestration (one central controller drives the sequence). Each service publishes and listens for events to keep the flow moving.

Real world

OrderService creates an order → publishes OrderCreated_Event. PaymentService listens, charges payment → publishes PaymentCompleted_Event. InventoryService listens, reserves stock → publishes InventoryReserved_Event. OrderService listens and marks the order Confirmed. If payment fails instead: a Customer_Cancelled_Event fires → OrderService cancels the order and publishes OrderCancelled_Event → InventoryService releases the stock it had reserved. This rollback-by-undo is called a compensating transaction — there's no single "commit," just a forward chain of local commits with a matching chain of local undos.

Trade-off: Saga avoids 2PC's synchronous, coordinator-blocking cost — but at the price of being genuinely harder to trace and debug, since the transaction's state now lives scattered across a chain of events rather than in one coordinator's head.

OAuth2 — authorization, not authentication

The "log in with Twitter" button, explained properly.

Clicking the tiny Twitter icon on a CNN article and logging in to Twitter tells Twitter it's okay for CNN to post to your feed — without CNN ever seeing your Twitter password. That's OAuth: instead of sharing credentials, it issues tokens that prove a scoped permission between a consumer app and a service provider (Twitter, Google, Facebook).

Authentication proves who you are. Authorization grants permission to specific data or actions. OAuth is about the second one — think of an OAuth token as a valet key: it starts the car and nothing more, it can't open the trunk or the glovebox, and some valet keys even cap how far the car can be driven. A website holding an OAuth token never holds your "main key."

Token types issued by the Authorization Server

  • Authorization Code — a short-lived code issued after login + consent; the client exchanges it for the real tokens.
  • Access Token — represents the granted permissions, has an expiry and a scope, is what actually gets sent to access protected resources.
  • Refresh Token — lets the client obtain a new Access Token once the old one expires, without forcing the user to log in again.

Flow

  1. User authenticates at the Authorization Server's login page.
  2. Consent screen — "Application wants access to your photo, allow it?"
  3. Authorization Server redirects back with an Authorization Code.
  4. Client exchanges the code for an Access Token (and optionally a Refresh Token) — the JWT access token is stored securely in the application's own vault.
  5. Every later resource request carries Authorization: Bearer <JWT access token>.
Note: the Authentication Service (LDAP/AD/Kerberos) and the Authorization Server are drawn combined in most simplified diagrams, but production systems commonly keep them as two separate services.

Correlation ID & centralized logging

Naveen's framing: one transaction touching three microservices leaves three separate logs — how do you debug that without it becoming, in his words, "a nightmare"?

A single transaction can involve Microservice 1, 2 and 3, each writing to its own independent log. Opening three different logs by hand — each already holding thousands of unrelated entries — to reconstruct one transaction's path does not scale.

Step one: Correlation ID solves tracing, not volume

The API Gateway generates a Correlation ID (e.g. X-Correlation-ID: 75) for the incoming request and passes it along to every microservice the transaction touches; each service includes that same id in every log line it writes for that transaction, and the final response echoes it back. This solves tracing — you now know which lines across which logs belong together — but it does not solve the deeper problem: with, say, 15 participating microservices, you'd still be opening 15 separate logs, each full of unrelated noise, to pull those lines out.

Step two: Centralized Logging pattern

Named design pattern: Centralized Logging — collect logs across all distributed microservices into one place (ELK: Elasticsearch/Logstash/Kibana, or AWS CloudWatch). Each microservice becomes a producer, pushing its log lines and events as messages onto a distributed queue (Kafka or RabbitMQ) instead of writing only to a local file. Three consumer services then read from that same queue by concern:

  • LogAgg Service — general/informational logs ("entered this method," routine flow).
  • Error Agg Service — only error-level events (a DB connection down, a failed call).
  • Alert Service — events promoted to alarm severity — e.g. a DB retry loop that's been going on too long gets escalated from "informational event" to "alarm."

Each writes to its own storage, and a visualization tool (Grafana is the one Naveen calls out by name) sits on top so a failing service shows up as a red flag on a dashboard instead of requiring anyone to open a log file at all.

Real world

A classmate's Java pricing/price-discovery microservice already runs Elasticsearch + Kibana this way. Their older, legacy C++ trading applications on Linux VMs still write to a shared log folder instead — searching for a trade id there means grepping across 10–20 separate log files by hand. Naveen's read on it: that manual-grep approach is what "very mature" engineering has moved away from, even at companies with otherwise world-class products — he described one large company where a single customer issue could bounce across 400–500 components and multiple regional teams simply because nobody had a clean centralized logging mechanism.

Also part of this: logs carry levels (info/debug through warning/error) so a customer or on-call engineer can turn off the noisy low-priority levels and keep only what they actually need to see.

Blue-Green & Canary deployment

How a microservice ships a new version without taking the service down.

Blue-Green deployment

Blue is the current live release taking all traffic (e.g. payment-service:v1); Green is the new release being deployed and tested (payment-service:v2) — Blue keeps serving customers the entire time Green is being validated.

Sequence: deploy v2 to Green → run the full suite of the customer's regression ("red-line") test scripts against Green while Blue still holds 100% of live traffic → once green, flip the load balancer to send traffic to Green → if failures show up, flip straight back to Blue immediately. The whole point is zero downtime — nobody experiences a maintenance window.

Real world — Rudra's question in class

Rudra asked: if a user is logged in during Blue and the load balancer flips to Green mid-session, does that user get logged out? Naveen's answer: this is genuinely debatable — an "in-flight session" question. Financial applications generally won't risk syncing session state across a distributed cache between the two versions, since that risks data-integrity issues; instead they simply force a re-login. Non-financial apps (an email client, say) can afford to take that chance more casually. In practice, many banks sidestep the whole question by doing this kind of switch during a scheduled overnight maintenance window (the 1–3am SMS alert) rather than live.

Compare: network hardware vendors (Cisco and others) have an equivalent concept called ISSU (In-Service Software Upgrade) for routers, since a router can never simply go down for maintenance the way an application server sometimes can — the whole internet behind it goes with it. Naveen's caveat: ISSU has a reputation for rarely working cleanly in practice, across vendors.

Canary deployment

Test a new release against a small percentage of real traffic before a full rollout — rather than Blue-Green's full test-suite-then-flip approach. Naveen's assessment: Canary is the weaker of the two, since some teams treat "ran a handful of test cases, looked fine" as sufficient before pushing to full production, without Blue-Green's built-in fallback path if something goes wrong.

More named patterns, good practices & trade-offs

The closing grab-bag Naveen flagged as common interview material.

A few more named patterns

  • Business Capability pattern — splitting a monolith into microservices along real business functions (Payment, Order, Shipping) rather than technical layers.
  • Subdomain / Bounded Context (DDD) — defining service boundaries around clear business contexts (e.g. a standalone Bank Balance Service), each owning its data, logic and domain rules completely.
  • Strangler Fig pattern — gradually migrating a monolith into microservices piece by piece, without a full rewrite.

Good practices (as an architect and for interviews)

  • Each service fully independent of the others, with clear boundaries.
  • Deployed independently, each registered with its own entry in the API Gateway's service registry.
  • Its own database — never a shared one.
  • Packaged as a container (its own Docker image) and deployed to the cloud.
  • Embrace parallelism through asynchronous communication (Kafka/RabbitMQ) — the thread issuing an event is never blocked waiting on the consumer.
  • Organize teams around microservices (a US team, an India team, a Japan team each owning their own services).
  • Design APIs around the domain and document them well.
  • Security via authentication and access tokens, validated against the distributed cache the Gateway and Auth Service share.
  • Circuit breaking wherever one microservice might be flaky.
  • Central log management with a correlation id running through every hop.

Advantages

Client code stays simple — it talks only to the API Gateway, which encapsulates the internal structure and cuts the number of round trips between client and application. Each service is independently deployable, ownable by a small team, and can expose a client-specific API shape.

Disadvantages

Routing rules need real upkeep; the Gateway is a potential single point of failure; keeping every routing/access rule in one place adds real operational complexity; and because each service owns its own database, you lose the ability to use foreign-key relationships across service boundaries.

GraphQL, gRPC & SOAP — alternatives to REST

REST isn't the only wire format an architect needs to recognize.

GraphQL

A query language and runtime, often described as REST's successor for API design. It treats data as a graph — nodes (entities like a user, product, post) connected by edges (relationships) — and exposes a single endpoint instead of many. The client specifies exactly which fields it wants; the server returns exactly that shape, nothing more, nothing less — eliminating REST's classic over-fetching (getting fields you didn't need) and under-fetching (needing a second call to get related data).

With GraphQL you can query data, run mutations (create/update/delete), and subscribe to real-time backend updates — all through that one endpoint, with a strongly-typed schema and no need for REST-style URL versioning.

API Rate Limiting

Why rate limiting exists — DoS and DDoS

Rate limiting predates microservices entirely — it's older than the API Gateway pattern itself, just commonly attached to it today.

If access to an API is unlimited, any user or bot can consume it as much as they want, at any time — starving out legitimate users. API rate limiting restricts access according to rules set by the API's owner, functioning as both a security control and a quality-of-service control: it ensures a sudden spike in users doesn't slow the whole system down for everyone.

Real world

A small Indian bank runs two servers (one active, one standby) and caps the system at 100 concurrent sessions. Naveen, Rudra and Nikhil log in — 97 sessions remain free. A hacker — a legitimate account holder, not an intruder using stolen credentials — runs a script that grabs all 97 remaining sessions in one shot. Tina and Ramesh can no longer log in at all. The bank restarts its server to free sessions; the hacker's script detects the restart and immediately re-grabs every session again. No legitimate user can transact. This is a textbook DoS (Denial of Service) attack — and the hacker's actual goal is usually extortion: keep the bank locked out until they pay up, since a proper fix can take weeks or months.

DoS vs DDoS

  • DoS — one source/IP overloads a server, website or network so legitimate users can't access it.
  • DDoS (Distributed) — the same goal, but from thousands or millions of machines simultaneously (a botnet); traffic looks like real users because it's geographically and IP-wise distributed, making it far harder to block with a simple IP rule.

Rate limiting is the defensive mechanism that keeps shared resources available against exactly this kind of abuse — in large-scale systems it protects underlying services and resources as a baseline, not an afterthought. Swiggy, Zomato, Uber, Google Search and ChatGPT all run on microservices and all rely on rate limiters; without them, DoS attacks on these platforms would already have happened long ago.

How a rejected request is handled

When a client exceeds its limit, an API has three options: queue the request until capacity frees up, allow it anyway at extra cost (rare — banks don't do this), or — most common — reject it, typically with HTTP 429 Too Many Requests. Naveen's product critique: a raw 429 is meaningless to a non-technical user; a well-designed app translates it into something like "servers are busy, please try again shortly."

DoS = one sourceDDoS = botnet, distributedsecurity + QoS control429 Too Many Requests

Four foundational rate-limiting techniques

The "as an architect, you pick and choose" toolkit — almost never used in isolation.

1. User rate limiting

The most common and intuitive form: a cap on requests per user per time window — e.g. no more than 10 requests/minute per login. Even a hacker with a single valid account is capped the same way as anyone else.

Real world

Naveen sends "bank balance," then "credit card balance," then "transfer money" as three of his ten allowed requests for the minute — once he hits 10, the eleventh is rejected until the window resets.

2. Concurrency rate limiting

Caps the number of parallel sessions a single user can hold at once (e.g. max 2 simultaneous sessions). This closes the loophole in pure user rate limiting: a hacker capped at 10 requests/minute per device simply logs in from hundreds of different devices and multiplies the attack — capping concurrent sessions per user blocks that.

3. Location / ID rate limiting

Used for location-based or demographic campaigns — traffic from outside the target region gets a smaller slice of capacity, protecting availability for the target audience.

Real world

An Indian election-news site reserves 80% of capacity for traffic originating in India and caps the remaining 20% for the rest of the world — global companies (Microsoft, Volvo, Ericsson, ABB) selling into India are all watching the results, and without this rule their traffic could crowd out Indian readers entirely.

4. Server rate limiting

A hard cap applied at the individual server level — e.g. "this server accepts no more than 100 requests/second," full stop, regardless of who's asking. Common in practice even when engineers don't consciously label it "server rate limiting."

How real systems combine these: user rate limiting is essentially always present; concurrency limiting layers on top of it to close the multi-device loophole; location-based limiting only applies to certain application types (a news site, not typically banking); server-level limiting sits underneath all of it as a hard backstop. Naveen's answer to "is it a mix of all these?" — yes, pick and choose per application, you rarely deploy just one.

Leaky Bucket algorithm

"The name sounds scary, you've probably already implemented this and didn't realise it."

A server with a fixed session capacity (say 100) also keeps a finite queue (say 20) for the overflow. Instead of instantly rejecting the 101st request, it's queued; as sessions free up, queued requests get pulled in and processed. Only once both the server capacity and the queue are full does a new request actually get rejected.

Real world

A bank's server handles 100 sessions but sees spikes to 120 at the start of every month. Instead of rejecting the extra 20, they're queued; as the original 100 free up, queued sessions get pulled in one by one until the queue drains. A 21st overflow request beyond the 20-slot queue is the one that actually gets rejected — ideally with a meaningful message, not a bare 429.

The advantage: it smooths bursty traffic into a near-constant, near-uniform flow into the backend, at the cost of a small added delay for queued requests (Naveen's example: a 1-second response might become 6–7 seconds during a burst). It's easy to implement on a single server or load balancer and is memory-efficient per user given the bounded queue size.

finite queuesmooths burstssmall added latencymemory-efficient

Token Bucket algorithm

Per-user budget that refills on a clock, rather than a server-wide queue.

Each user gets a bucket holding N tokens. Every request consumes one token; once the bucket is empty, further requests are discarded until the bucket is replenished back to N at a fixed interval. Easily implemented with a hash map keyed per user.

Vs. leaky bucket: leaky bucket is about smoothing a shared queue at the server; token bucket is a straightforward per-user request allowance that resets on a timer — no queueing, just allow-or-discard against a running balance.
N tokens per user1 token per requestdiscard when emptyfixed-interval refill

Fixed Window Counter

The moving-train analogy: a wagon can only board passengers for its fixed one-minute window.

Time is divided into fixed windows (e.g. every 60 seconds); a counter increments on every request within the current window and resets to zero when the window rolls over. Implemented as a simple key-value pair where the key is the time window and the value is the request count — no queueing at all, requests beyond the limit are simply discarded.

Real world

Limit: 5 requests/minute. At 12:00:00–12:00:59 only 5 requests are allowed; the 6th within that same window is dropped, even if it arrives at 12:00:59. At 12:01:00 the counter resets to zero and 5 fresh requests are allowed again.

The boundary problem: because windows are fixed and reset abruptly, a client can send a full quota right at the end of one window and another full quota right at the start of the next — doubling the effective burst right across the boundary. The fixed window algorithm has no memory of what happened just before the reset.
key = time window, value = countno queue, hard discardboundary burst problem

Sliding Window Log

Fixes the boundary problem of fixed windows by tracking exact timestamps instead of bucketing into rigid slots.

Every request's timestamp is logged (typically in a sorted hash set/table). On a new request, the algorithm sums how many logged timestamps fall within the trailing window (e.g. the last 60 seconds) — if that sum would exceed the threshold, the new request is held or rejected. Logs older than the window are discarded as they age out.

Trade-off: precise enforcement, no boundary-burst problem — but expensive. Storing an unbounded number of per-consumer logs, and recomputing a summation across potentially a whole server cluster on every single request, doesn't scale well against large bursts or DoS-scale traffic.

Priority Session Rate Limiting & Drop Low-Priority Sessions

The architect-level decision: when the system is saturated, whose request gets killed first?

Reads vs writes

In banking, most traffic is reads (checking balance, statements) and a small minority is writes (actually transferring money — mutating the database). A typical split reserves 80% capacity for reads, 20% for writes — even though writes are the minority, that 20% is protected because a failed write is far more painful for a legitimate user than a failed read.

Real world

If Naveen's bank-balance check fails because the server is busy, he shrugs and checks again tomorrow. If an accountant's payroll transfer or GST payment fails because the server is busy, that's a real, urgent problem — hence writes get a protected capacity slice even though they're rarer.

Drop low-priority sessions

If write traffic exceeds its reserved 20% (say the system is at 100/100 with reads at 80 and writes climbing past 20), the system starts killing read sessions to make room for incoming writes — the total stays capped at 100, but the read/write mix shifts in favour of writes as demand for writes increases.

Where this does NOT apply: trading platforms generally don't implement this — killing a session mid-trade risks real financial loss and forced logout, and stock-market trading is regulated by SEBI (Securities and Exchange Board of India); giving paying customers higher session priority over others is the kind of rule a broker would need to clear with the regulator first, not something an architect can unilaterally decide.

Where rate limiters actually live

Rudra's question in class: is this a Gateway-only concept, or does it show up elsewhere too?

Historically (the "olden world"), rate limiting sat directly on the web server: client → web server → rate limiter → API service, with the server itself enforcing limits before passing traffic on. Today, the rate limiter is typically integrated directly into the API Gateway, alongside the auth service — the same place all other cross-cutting concerns live.

Centralized rate limiter vs multiple Gateways

If a system has multiple API Gateway instances, they all need a shared, consistent view of how many requests a given user has already made — otherwise each Gateway enforces its limit independently and the real combined limit balloons. The clean answer: keep one centralized rate limiter (which may internally run its own master/worker nodes for scale) rather than making every Gateway instance, or every per-Gateway rate limiter, talk to each other to stay in sync. Multiple API Gateways are workable and common, but they bring their own set of problems — covered later alongside load balancer topologies for microservices.

Protecting the API Gateway itself

  • TLS authentication
  • Web Application Firewall (WAF) configuration
  • Throttling targets set explicitly on the Gateway
  • Restricting API access to only originate from within a VPC (Virtual Private Cloud) — a secure, isolated private cloud hosted within a public cloud, combining public-cloud scalability with private-cloud data isolation.
Architect's mental model: microservices should stay focused purely on business logic. Auth, rate limiting, load balancing, caching — every cross-cutting concern — gets pushed up into the Gateway layer so individual services never have to think about it.

Event-Driven Architecture & Kafka

Event-Driven Architecture (EDA)

Decoupled communication that replaces the request/response contract with publish-and-forget.

An event is a change of state or an update — an item placed in a shopping cart, a stock price tick, a discharge summary being finalized. An event can either carry the state itself (the item, its price, a delivery address) or just be an identifier that something happened (a notification that an order shipped). Event-Driven Architecture uses events to trigger and communicate between decoupled services, and is the natural fit for microservices.

EDA has three components: event producers publish an event to an event router (the broker), which filters and pushes it to event consumers. Producer and consumer services are decoupled — each can be scaled, updated and deployed independently.

Why not just use an API call?

With a REST API call, the caller needs to know the callee's dependencies and parameters, send a properly formatted request, then wait for the response before proceeding — every exchange is a request and a response. With EDA, a producer sends its event without needing to know what happens after; the router decides where it goes. Think of the router like a WiFi router — it receives data and distributes it to whichever devices need it, in real time. Consumers (also called sinks) receive events to process without requesting them, and every consuming service works independently — so events are processed asynchronously. The flow of event data across producer → router → consumer is called the event channel.

Real world — Swiggy order flow

Naveen adds a biryani to his cart on Swiggy (event: cart created), applies a ₹200 discount coupon (event: coupon applied, ₹50 off), and the order total drops from ₹400 to ₹350 (event: sale = ₹350). Each of these is a separate event a restaurant's order system reacts to independently — and Swiggy runs this same flow for roughly 15,000 people ordering from one restaurant at once, none of whom block on each other.

Common EDA use cases

  • Data replication — one event, shared to multiple services that each copy it into their own database.
  • Parallel processing — one event triggers multiple processes that execute asynchronously of each other.
  • Real-time monitoring — systems emit events on state changes so anomalies and suspicious activity can be scanned for as they happen.
  • Interoperability — events persist and propagate regardless of which language a service is written in.
  • Redundancy — if a service is down, its events persist in the router until it's back to consume them.
  • Microservices — EDA is the standard way to share information between decoupled services at scale.

EDA — advantages and disadvantages

Decoupling isn't free; it trades direct dependencies for eventual consistency and an extra hop.

Advantages

  • Decoupling — services only need to know about events, not about each other; the broker delegates the right events to the right systems.
  • Immutability — events can't be changed once created, so multiple services can consume the same event without one service corrupting it for another.
  • Persistability — in a traditional request/response model, Service 1 calling a down Service 2 simply fails; with events, the broker holds the event until Service 2 is back, avoiding a single point of failure.
  • Scalability — one event can trigger multiple consumers in parallel, and producers/consumers can be added or removed without touching each other's logic.
  • Real-time workflows — EDA reacts as events occur, supporting near-real-time responses for purchases, live chat, and similar interactions.

Disadvantages

  • Performance — the router is a "middle man" between producer and consumer, which can be slower than a direct call; there's also a trade-off between sending full event payloads (slower transmission, most consumers won't need it all) versus slim notifications (consumers then have to query for the missing data themselves).
  • Eventual consistency — different consumers react to the same event at different times depending on their own processing speed; every service eventually finishes, but not at the same moment.
  • Complexity — decoupling removes direct dependency tracking, but that also makes it harder to trace the status of an event across many independent consumers compared to a direct call chain.
Rudra's question in class: if a consumer is offline when an event fires, is the event lost? Naveen's answer: no — that's exactly what persistence buys you. The broker retains the event (subject to however long its retention/TTL is configured), and a consumer that comes back can pick it up from where it left off using its committed offset.

What is Apache Kafka

A distributed, partitioned, replicated commit log — the broker implementation EDA is usually drawn against.

Kafka's architecture — producers, brokers, partitions, consumers

Kafka runs on a cluster of one or more brokers; every topic's partitions are spread across that cluster.

A Kafka cluster can have multiple brokers/event routers, and one is elected as the main broker. Partitions of all topics are distributed across the cluster's nodes, and (as covered under replication) additionally replicated to more than one broker so the cluster tolerates node failure.

Real world — hospital event stream

Message keys & ordering

If a producer attaches a key to a message, every message with that key always lands on the same partition, in the order sent — that's how you guarantee ordering for a related sequence of events (e.g. all events for order 1234: prepared → shipped → delivered land in the same partition, in that order). Segments, indexes & durability

A partition isn't one giant file — it's a rolling chain of bounded segment files on disk.

Kafka brokers split each partition into segments, each stored as a single data file on the broker's disk. By default a segment closes and a new one opens once it hits 1 GB of data or one week, whichever comes first.

To let consumers fetch from any available offset quickly, Kafka keeps two indexes per segment: an offset→position index (which part of the segment file to read for a given offset) and a timestamp→offset index (find messages as of a specific time).

Durability comes from Kafka being a distributed commit log: messages persist to disk as fast as possible. Each message can also carry a time-to-live — e.g. keep events for 24 hours — so a consumer that was briefly down (say, back online after 2 hours) can still catch up from where it left off using its committed offset, but a consumer down longer than the TTL will have missed events purged from the broker.

Real world — Twitter/X notification

Elon Musk tweets a Tesla announcement; the event lands across many partitions for millions of registered consumers. If a consumer's device is offline and the event ages out of the broker (say after 48 hours), the notification is lost — but the tweet itself isn't: it lives in Twitter's own database, and the app fetches it directly from there next time it opens. Kafka's broker only ever promised to hold the notification event for a bounded time, not to be the system of record.

Consumer groups & parallelism

One partition, one consumer — per group. That single rule is what keeps Kafka from stampeding its own data.

A consumer group is a logical grouping of consumers sharing a common group id. When a group consumes a topic's partitions, Kafka guarantees each partition is read by exactly one consumer instance within that group — no two consumers in the same group ever read the same partition. Multiple consumer groups can independently subscribe to the same topic without competing: each group gets its own full copy of the data (e.g. a "mobile" consumer group and a "web" consumer group both read the same connection-events topic, independently).

Real world — Rudra's class exercise

Naveen set up a LinkedIn-style consumer group with 3 partitions: Nikhil reads only partition 1, Rudra only partition 2, Naveen only partition 3 — strictly, no crossover. When Rajesh and Tina join the same consumer group, there's no "default" partition for them to fall back to (Rudra's first guess) — the only fix is to scale the number of partitions to match, adding partition 4 for Rajesh and partition 5 for Tina. Naveen's rule: the number of people (consumer instances) in your consumer group should equal the number of partitions in your architecture, or the extra consumers simply have nowhere to read from. Rudra also asked what happens if a partition becomes unavailable — Naveen's answer: replication kicks in, and Kafka transparently serves from a replica held elsewhere.

This exclusivity is deliberate: if several consumers in the same group could read the same partition, they'd stamp on each other's progress and slow the whole group down. The maximum parallelism of a group is therefore capped at the number of partitions on that topic — more partitions and more consumer instances is the only way to scale throughput further.

Replication, fault tolerance & acknowledgements

Every partition has a leader and, usually, a couple of followers standing by.

Kafka keeps more than one copy of the same partition across multiple brokers — each redundant copy is a replica. If a broker fails, Kafka keeps serving consumers from the replicas that broker used to own. The replication factor is the number of copies per partition: a factor of 1 means no replication at all (one copy, no protection); a factor of 3 means three copies — one leader and two followers.

Firewalls

The 25-year-old first line of defense: a barrier between trusted internal networks and untrusted outside ones.

A firewall monitors incoming/outgoing traffic and decides whether to allow or block it against a defined rule set. It can be hardware, software, SaaS, or public/private cloud (virtual). Three outcomes per packet: Accept (allow), Reject (block, reply with an unreachable error), Drop (block, no reply at all).

Advantages

  • Blocks infiltration/eavesdropping from oddly-behaving sources and advanced persistent threats

  • Workplace restrictions — block social media/certain services on the company network

Packet filtering techniques

The policy toolkit a firewall administrator actually configures.

  • Packet filtering firewall — filters packets against a predefined rule set; can check source IP to prevent IP-spoofing attacks. Operates at Layer 4 (with some Layer-3 awareness).
  • Static packet filtering — fixed, manually-set rules; practical for smaller networks with consistent traffic, low administrative overhead, but inflexible.
  • Dynamic packet filtering — opens/closes ports as needed (useful for protocols like FTP that allocate ports dynamically); more flexible without sacrificing functionality.
  • Stateless — evaluates each packet in isolation, no memory of previous/future packets.
  • Stateful — tracks active connections and decides based on the state of the traffic, not just the single packet.
  • Rate limiting at the firewall — caps the packet rate destined for a device/network to blunt flood/DoS attacks.
  • Subnet-level rules — rules can restrict traffic between subnets, containing breaches and segmenting by department or sensitivity.
Real world — subnet segmentation by department

A company network is split into Subnet-1 (Engineering, running a 10-server lab), Subnet-2 (HR & Finance), Subnet-3 (Marketing & Sales) and Subnet-4 (CEOs) — each with its own firewall rules, so an Engineering employee's compromised machine can't simply reach the Finance subnet's servers or the CEOs' subnet just because they're on the same company network.

WAF — Web Application Firewall

A Layer-7 reverse proxy that stands between the internet and the application, not just the network.

A WAF is a specialized protection layer for web applications, servers and APIs — it examines and filters HTTP traffic to guard against threats like cross-site scripting (XSS), SQL injection and file inclusion. Unlike a network firewall (Layer 4), a WAF operates at Layer 7, targeting application-layer threats specifically. A WAF is a type of reverse proxy: where a regular proxy protects a client's identity via an intermediary, a WAF protects the server by making every client pass through it first.

Real world — Swiggy / Zomato / Uber scale

Picture three companies each with their own server fleet behind a WAF — Swiggy running 20 servers, Zomato 30, Uber 60. Every one of those fleets sits behind its own WAF, and only after clearing the WAF does traffic reach the load balancer, then the web servers, then the database. Naveen's framing: "your WAF is sitting here... this guy is a hacker... you have to filter them out here."

WAF value comes partly from how fast its policies can be changed — during a DDoS attack, rate limiting can be added by editing WAF policy alone, without touching application code.

OAuth — authorization, not authentication

The valet-key model: a limited-access token instead of handing over your actual password.

Instead of sharing password data, OAuth uses authorization tokens to prove identity between a consumer and a service provider (Twitter, Facebook, Google). OAuth is about authorization, not authentication — authentication proves who you are; authorization grants permission to access specific data or features once you're already known.

Real world — tweeting a CNN article

Clicking the Twitter icon on a CNN article pops up a Twitter login. Logging in there tells Twitter it's okay for CNN.com to post to your feed — without ever handing CNN.com your Twitter password. Convenient (no new CNN account needed) and safer (a CNN breach can't leak your Twitter credentials, because CNN never had them).

Valet key analogy: an OAuth token is like the separate valet key for your car — it starts the car but can't open the trunk or glove box, and can even be limited to a certain mileage. The application gets a "valet key" to your data, never the "main key."

OAuth flow

  1. The application requests authorization to access a protected resource.
  2. The user authorizes the request.
  3. The application presents proof of that authorization to the service provider in exchange for an access token.
  4. The user is redirected to the service provider to grant permission.
  5. Once approved, the application receives the access token.
  6. The application uses that token to request the protected resource from the service provider.
Real world — K-Bank expenditure app

A third-party "App" wants to build an expenditure graph from K-Bank data. App → Bank Auth/Authorization Server: authorization request. User authorizes it at the bank's own server (never through the App). Bank → App: an authorization grant (with a code). App exchanges that code for an Access Token, encoded as a JWT. The App then presents that JWT to the K-Bank Resource Server to actually pull the protected data — the App never sees the user's bank password at any point.

TLS handshake

Nine steps that turn "hello" into a shared symmetric session key, without ever sending that key over the wire.

  1. Client Hello — client sends TLS version, supported cipher suites, and a random client nonce.
  2. Server Hello — server responds with its TLS version, chosen cipher suite, a server nonce, and its SSL/TLS certificate (containing the server's public key).
  3. Client validates the certificate against a Certificate Authority (a trusted entity that issues, validates and revokes digital certificates) — checks validity dates, verifies the CA's signature using the CA's public key, and checks revocation status (OCSP/CRL). If validation fails, the connection is aborted.
  4. Client sends the pre-master secret — another random value, encrypted with the server's public key so only the server's private key can decrypt it.
  5. Server decrypts the pre-master secret using its private key.
  6. Both sides generate the session key independently from the client nonce + server nonce + pre-master secret — they should arrive at identical results without ever transmitting the session key itself.
  7. Client sends "Finished", encrypted with the new session key.
  8. Server sends "Finished", encrypted with the session key.
  9. Handshake complete — the rest of the conversation uses fast symmetric encryption via the shared session key, instead of the slower asymmetric public/private key operations used just to establish it.
Real world — RSA lock-and-key analogy

Public/private key pairs work like different real-world locks: a Godrej padlock — anyone can use the public key to lock it (encrypt), but only the one private key unlocks it (decrypt). A bank account number is public (anyone can send money to it), but only the password lets you withdraw. An email address is public, but only you hold the password to read what's inside. The pattern is always: encrypt with the public key, decrypt only with the matching private key.

Rudra's question in class: what's actually inside a digital certificate? Naveen's answer: essentially the server's public key plus identity details, signed by the issuing CA — it's what lets the client trust that "this public key really belongs to this server" without having met the server before. Rudra also asked how mTLS (mutual TLS) differs from regular TLS: in the flow above, only the server presents a certificate (one-way trust); in mTLS, the client also presents its own digital certificate so both sides authenticate each other — more secure, but issuing and managing client-side certificates is a real added cost, which is why one-way TLS is the far more common default.

Protecting public APIs from DoS

A layered toolkit — no single control here is sufficient by itself.

  • Lockout / progressive delays — lock an IP out for X minutes after N failed logins (e.g. via Tomcat's LockoutRealm).
  • OTP — forces a human-in-the-loop step (email/phone/distorted on-screen code) that a script can't trivially automate around.

  • Odd-hours traffic detection — large traffic spikes at unusual hours/weekends can be flagged if not normally expected.

  • Behavioral-profile detection — flood from users sharing one device type, geolocation or browser version.
  • Gradual throttling — reduce a user's allowed rate as they approach the limit instead of an outright block.
  • Whitelist/blacklist IPs, and real-time monitoring with alerts for anomalies.

Zero Trust — "never trust, always verify"

Eliminates implicit trust and continuously validates every stage of a digital interaction.

Zero Trust is a strategic approach to cybersecurity designed for modern, distributed environments: strong authentication, network segmentation, preventing lateral movement, Layer-7 threat prevention, and granular "least access" policies. Unlike a VPN — which grants complete access to a LAN once connected — Zero Trust Network Access (ZTNA) defaults to deny, granting only the specific access a user has explicitly been given.

Pillars of Zero Trust

  • Identity — least-privileged access, login credentials plus multi-factor authentication.
  • Devices — verifying device integrity (e.g. antivirus is current) before trusting it.
  • Networks — micro-segmentation instead of implicit trust in traditional network zones; each segment carries its own policy and least-privilege access, limiting how far an attacker can move laterally.
  • Applications & workloads — access granted per-application based on identity, device compliance and other attributes; workloads (app + data + services + compute, wherever they run — cloud, on-prem, containers, VMs, microservices) are categorized by criticality (customer-facing vs. business-critical core, etc).
  • Data — a data-centric approach: classify data by sensitivity (public/internal/confidential/restricted) and maintain an inventory of data assets (location, owner, classification).
ICS shorthand for the model: don't trust anyone by default, even someone in the same office (Identity) — grant least privilege for that session only (Context) — verify device compliance, e.g. antivirus is current (Security).

How ZTNA actually works

A proxy-based architecture connects users directly to applications, never to the network itself.

  1. Verify identity and context — the connection is terminated first; ZTNA establishes the "who, what, where" of the request before anything else happens, regardless of the underlying network.
  2. Control risk — once identity/context are verified and micro-segmentation rules applied, ZTNA evaluates risk and inspects the traffic for threats and sensitive data.
  3. Enforce policy — a risk score (user behavior, device health, location) determines access; if within acceptable limits, a secure connection is established to the internet, SaaS app, or IaaS/PaaS environment.

The Trust Broker is decentralized, not a single device: its control plane handles management, intelligence and monitoring of ZTNA policies, while its data plane carries the actual connection between user and application through a tunnel it creates.

Micro-segmentation

Divides a network into small, independently-secured trust zones with identity-based access control and granular, fine-grained policy — implemented via network-based tools (VLANs, firewalls, SDN), host-based tools (endpoint agents/firewalls), or cloud-native tools (security groups, service meshes, Kubernetes).

Tunnels in ZTNA

Tunnels (TLS, WireGuard, IPSec) encrypt traffic end to end, are only established after identity/device-health verification (no implicit trust just for being "inside" the network), and grant access to one specific app rather than the whole network — reducing lateral-movement risk if a device is compromised.

Real world — least privilege at Amazon's USA office

Naveen's laptop connects via a VPN tunnel with antivirus checked, landing him in the Engineering subnet with least-privilege access to the 5-server lab. A different subnet holds HR, another holds Finance, another holds the CEO's office (accessible only to the CFO, the CEO's admin, the CEO himself, and one board member) — each reachable only by the people explicitly granted access by their manager, never by default. If a hacker compromises a low-privilege machine in the lab (2 servers), the least-privilege boundary stops them from pivoting into Finance or the CEO's subnet.

VPNs, tunneling & IPSec

A VPN extends a private network to users who aren't physically on it.

A VPN anonymizes traffic and location, extending secure access to a private network (e.g. an office network) to off-site users over the internet, by creating a link between a VPN client and VPN server via a tunnel. Tunneling encapsulates one protocol inside another — think of a sandwich, where the outer bread is one protocol and the filling is another. In L2TP (Layer-2 Tunneling Protocol), a Layer-3 protocol (IP) carries a Layer-2 payload (an Ethernet frame, complete with MAC address, ARP packets, non-IP protocols).

Single Sign-On (SSO)

Authenticate once with the Identity Provider, get tokens for everything else without logging in again.

  1. User tries to access an SSO-enabled application.
  2. The application checks if the user is already authenticated; if not, it redirects to the SSO authentication server (Identity Provider / IdP).
  3. User enters credentials at the IdP's login page.
  4. The IdP verifies the credentials.
  5. On success, the IdP issues an authentication token/session — typically a JWT.
  6. User is redirected back to the original service, carrying that token.
  7. The service validates the token with the SSO authentication server.
  8. Once validated, access is granted; the service may establish its own session for continued access.
  9. If the user then tries another service in the same SSO domain, the same flow runs again — but since a valid session already exists at the IdP, a new token is issued for that service without asking the user to log in again.
  10. Session management is centralized — logging out of one service typically logs the user out of every service in the SSO domain.

SSO is commonly implemented with OAuth, OIDC and JWT.
